RLS, more or less

Say who sees what.
Prove it holds.
Then compile it.

MLS states who may see and change which rows of a Postgres database, once. It proves the guarantees you care about with an SMT solver before anything is deployed, and compiles the rules to ordinary RLS policies, CHECKs, foreign keys and triggers, each tested against the real server. Keep your tables; replace your policies.

Why it exists

Three ways hand-written RLS goes wrong.

Each is easy to see once someone points at it, and hard to see in a review of forty policies. MLS takes them in turn.

i.

A second policy opens a second door.

Postgres ORs permissive policies. Add "admins read their team's notes" next to "members read their team's notes", and isolation now rests on every admin also being a member: a fact in another table, enforced by nothing.

→ the prover finds it, with a counterexample
ii.

NULL is not false.

A policy admits a row only when its expression is TRUE; a CHECK rejects one only when it is FALSE. The same expression means two things in two places, and a NULL column falls in the gap.

-- archived IS NULL:
using (not archived = 1) -- hidden
check (not archived = 1) -- let in
→ three-valued semantics, one meaning everywhere
iii.

The policy is right, and slow.

Membership checks that return the same rows can run in a fraction of a millisecond or in hundreds, depending on how they're written. Nothing in the policy text tells you which kind you wrote.

→ the compiler emits only the shape that stays on the index
How it works

Rules are enforced. Properties are proved.

A spec says who may see and change which rows, and which invariants the data must satisfy. The rules are what gets enforced; the properties are what gets proved about them, whatever the rules end up being. Everything below is real output from the guide's tour, which the test suite replays.

1 Write the rules · .mls

One line per rule, in a language small enough to prove.

Membership, comparisons with the current user or constants, hierarchies with a declared depth, time windows, column rules. No joins, no arithmetic, no functions in predicates: that's what keeps every proof decidable. Anything else goes in an explicit opaque block, and every proof that needs it says so.

The terse syntax and the JSON are the same model; mls fmt converts.

2 State the promises · properties

Say what must never happen, and what must always work.

Tenant isolation, immutable columns, monotonicity in membership, write ⊆ read, least privilege, inductive invariants, role separation, custom upper bounds. And must_allow, the lower bound: a spec that denies everything satisfies every safety property, so you also say what a role must be able to do.

3 Prove · mls prove

A failed proof is a database you can read aloud.

The solver checks each property against every possible database, not the rows you happened to test with. When one fails you get a concrete situation that breaks it, small enough to read in a meeting. Here, a member of team 3 can't read their team's note, because its archived is NULL and the restrictive policy said not archived = 1.

mls prove exits 2 when anything is refuted, so CI fails the build.

4 Three values, one meaning

TRUE, FALSE, and UNKNOWN, everywhere.

Every predicate has SQL's three-valued meaning, in the prover and in the compiler. The solver works on (is-true, is-false) pairs, so it can't take the two-valued shortcut that hides the NULL. And the compiler normalizes every target to the same reading: CHECK ((p) IS TRUE), a trigger's IF NOT ((p) IS TRUE). A rule admits the same rows whether it's enforced by a policy, a constraint or a trigger.

5 Compile · mls compile

One SQL script, in the one shape that stays fast.

Policies, CHECKs, composite foreign keys, triggers from fixed templates, column privileges, indexes, grants, and hardening: row-level security forced on every table, so the owner obeys the policies too. Every statement ends with the rule it came from.

6 Test against the real thing · mls test

The proofs are about the model. The tests tie the model to Postgres.

Every compiler template has a differential test: generated databases and statements, run through MLS's own evaluator and through the compiled objects on Postgres 15, 16, 17 and 18, which must agree row for row. Examples also deploy and pass as a role that is not a superuser, the way managed Postgres services run them.

And every template has a mutation: a deliberately wrong version the differential test must catch. A test that still passes against a broken template isn't testing anything, so it fails the build.

7 Approve in English · mls explain

Nobody has to read the spec to approve it.

The person who owns the requirements approves the properties and the scenarios, in plain English. Each sentence is a promise the solver has checked. When a spec changes, mls diff lists every change in effect, for whom, with an example row.

That's also what makes it safe to let an LLM write the spec: mls generate turns requirement sentences into rules and properties, and any relation the schema lacks, and repairs them against the prover until they hold.

The common case

Keep your tables. Replace your policies.

Most projects already have a database: tables and data that stay where they are, and policies written by hand and never proved. The takeover keeps the schema and lets MLS own the policies. The user guide walks through it with every command with what it prints, and the test suite replays it.

i.

Record what the old policies allow

Before touching anything, import today's behaviour as a spec. It's what you compare against, and what you roll back to.

$ mls import --dsn "$DATABASE_URL" --out before.mls
ii.

Import the skeleton

Tables, keys, readable CHECKs, membership tables and the identity adapter, read from the catalog. No policy is imported. MLS adds rules to these tables and never recreates them.

$ mls import --dsn "$DATABASE_URL" --policies discard --out spec.mls
spec.mls: imported 5 table(s), 28 note(s)
iii.

Read the notes, close the bypass paths

Every policy the deploy will drop, the tables with RLS off today, and the bypass paths: a view that isn't security_invoker, a SECURITY DEFINER function an app role can call. Each note ends with its fix.

iv.

State the requirements; the LLM writes the rest

Start from mls explain before.mls, today's policies in English, and write one sentence per grant. mls generate --skeleton spec.mls adds the relations the schema lacks, writes the rules and properties, proves them, and gives you the guarantees to approve in plain English.

v.

Prove, then compare

Prove until every property holds, then diff against the old behaviour: every change in effect, with an example, for the people who own the requirements.

$ mls diff before.mls spec.mls
- authenticated can now read rows of tasks
  that were not allowed before
  - before: `false`
  - after: `in_project(@uid, project_id)`
vi.

Preview, deploy, confirm

mls preflight finds rows the new constraints would reject; mls drift lists what the deploy drops and creates. The script runs in one transaction and names each policy it drops. Afterwards, drift is clean and every table is proved.

$ mls status spec.mls --dsn "$DATABASE_URL"
profiles: proved (P5, P6)
projects: proved (P1, P3)
tasks: proved (P2, P4, P9)
team_members: proved (P8)
teams: proved (P7)
Stated assumptions

It tells you what it didn't prove.

A proof is only as good as what it assumes, so every proof report states its assumptions, and MLS refuses rather than silently enforce something weaker.

Never silently weaker

If a target can't enforce a construct soundly, the compiler refuses with an error that says what's wrong, where, and what to write instead. Errors are written for an LLM to act on, which also makes them good for people.

Opaque means conditional

Raw SQL is allowed only in an explicit opaque block. The prover treats it as a black box, and a proof that actually needs it is reported as conditional on it, by name. Opaque blocks are outside every performance guarantee too.

Trusted roles, and the ways around

Superusers and BYPASSRLS roles bypass everything, and every report says so. Non-invoker views and SECURITY DEFINER functions over a governed table are reported as bypass paths, never rewritten: they're your objects.

A small language, on purpose

No construct goes in whose proofs would leave a decidable fragment without a declared bound. Hierarchies have a maximum depth; a column some users see only on some rows becomes its own table, because there is no masking construct.

Measured on our own words

With claude-opus-5-5, the LLM loop ended proved and equivalent to the reference on all 37 seed cases in its latest run, and repaired all 229 mutated specs. But we wrote those requirement texts ourselves. A corpus of real ones is the open question.

Alpha, and Postgres only

Version 0.1: the spec language and the CLI may change before 1.0; the semantics and the design decisions are settled. Postgres 15 to 18 only. Cardinality limits rely on a parent-row lock and are correct under READ COMMITTED; the report says so.

Get started

Clone it. Prove something.

A Python 3.12+ package managed with uv. Checking and proving need no database; testing uses Docker or a server you provide.

git clone https://github.com/neptunestation-com/more_ls && cd more_ls && uv sync --all-extras && uv run mls prove examples/team_notes.mls

Already running Postgres in production? Start with taking over the schema you have. New schema? The guide's ten-minute tour builds a spec one requirement at a time.
